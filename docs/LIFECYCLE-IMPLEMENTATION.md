# v0.4 实施契约：管理、公众号发表及反馈

2026-09-08，承接用户“继续完善后执行”及首个渠道“微信公众号”的选择。原始章程保留；其 MVP 阶段之后的 Publication/Learning 现在进入实施主线。

本轮选择：保留已验证的 Markdown 编辑内核，以一个公众号流程接上前后环节。研究仍可由 Gemini Notebook/Open Notebook 等外部工具完成，再显式捕获原始来源；不要求作者迁移全部知识库，也不再建设一套通用聊天/RAG。

| 环节 | 本轮落地 | 边界 |
|---|---|---|
| 管理 | 统一来源分组、跨项目摘录复用、项目计划日期 | 来源 URL/本地路径为身份；移动来源文件需要人工核对 |
| 来源维护 | 读取原笔记哈希，标记变更/缺失，比较刷新、保存旧快照，阻止过期审查与投递 | 外部网页不自动抓取；影响范围按整个关联项目保守列出 |
| 创作审查 | 继续原四阶段 Agent 与人工五轴审查、批准版本绑定 | 不声称生成质量胜过 Notebook；复杂编辑仍用原生编辑器 |
| 公众号 | 账号本地配置、封面上传、HTML 预览、草稿投递及回读、二次确认发表、状态查询及文章回读 | 单篇图文；正文图片与复杂排版暂用微信后台 |
| 恢复 | Markdown outbox、提交前意图落盘、ACK 恢复文件、未知结果只读核验、禁止重复确认和同版重复投递 | 丢失远端 ID 时可能需要人工找回，不承诺通用 exactly-once |
| 反馈 | 来源/时间/观察/建议绑定 Publication；人工接受或拒绝；已接受经验进入下一项目 | 暂不自动读取微信统计；不自动改写 CONTENT.md |
| 无接口权限 | 已批准 Markdown 交接及独立人工发表登记 | 明确标注未经 API 核验 |

投递状态：PREPARED → SENDING → REMOTE_DRAFT；再创建独立发表意图 PREPARED → SENDING → SUBMITTED → PUBLISHED。失败分 FAILED、UNKNOWN、CONFLICT；取消只适用于 PREPARED；删除/封禁显示 WITHDRAWN。得到 publish_id 不能标记成功，日期计划也不会触发定时发表。

所有外部写入都需要界面上的具体预览和人工确认；模型不能调用此流程为用户批准。网络期间不持有 Vault 写锁；写入前与回读后都核对版本。并发本地修改不会抹掉已发生的远端事实，但不会提升当前项目版本为已发表。所有稿件都有当前回执后项目才进入 PUBLISHED。

凭据使用当前 Windows 用户 DPAPI 或显式环境变量；令牌只保存在内存。请求固定微信 API 主机、不跟随重定向、不把外部 errmsg 原样反射给用户。部署包通过白名单构建，排除 Vault、运行目录和凭据。

选择微信带来的取舍：通过官方接口降低维护成本，但受账号认证、IP 白名单、排版限制及不支持条件写入制约。没有复制 Ailu 的多平台适配面；也没有把“可以导出”写成“已打通真实平台”。真实联调需账号本地配置，见 [接入步骤](WECHAT-SETUP.md)；软件和实际平台验收分列见 [验收报告](VALIDATION-v0.4.md)。

后续顺序：先完成真实账号首篇闭环 → 记录实际排版差异与确认耗时 → 补正文图片与渠道样式 → 按权限接入微信数据统计 → 用连续两篇任务比较留存和总成本 → 再决定 Open Notebook API 适配和更多渠道。未经实际证据，不宣称已形成护城河或用户留存。
