# 竞争判断纠偏：Gemini Notebook、Open Notebook 与完整内容生命周期

2026-09-08。依据用户对 v0.3 的质疑，重新核查官方产品文档、章程与当前代码。本文件修正 MARKET-STRATEGY.md 中将“批准稿交接”作为主要终点、将发布反馈长期后置的建议。它记录 v0.3 阶段的产品决策修正；当前 v0.4 实施与验证请见 [实施契约](LIFECYCLE-IMPLEMENTATION.md) 和 [验收报告](VALIDATION-v0.4.md)。以下“当前 v0.3”均为修正时的历史基线。

## 1. 当前版本为什么不足以吸引用户

如果任务是读资料、整理知识、生成有引用的内容，Gemini Notebook 和 Open Notebook 的已公开能力比当前 OpenContent 完整。没有足够证据声称我们的生成质量、研究准确性或使用成本更好。先前漏掉这两类直接替代品，使“有出处的写作”这一定位显得比实际更有差异。

| 已查证事实 | 对项目的影响 |
|---|---|
| Google 当前官方帮助使用 Gemini Notebook 名称；支持源资料、研究报告、多种 Studio 输出、Docs/Sheets 导出及分享。[官方说明](https://support.google.com/gemininotebook/answer/16206563?hl=en) | 不能将它描述成只会问答的阅读器；用户已有从研究到内容输出的路径 |
| 支持检索并导入研究来源，包含 Deep Research。[来源文档](https://support.google.com/gemininotebook/answer/16215270?hl=en) | 我们目前只处理捕获材料，研究范围明显更窄 |
| Google 提供引用定位；笔记也能生成大纲和获得论证反馈。[聊天](https://support.google.com/gemininotebook/answer/16179559?hl=en)、[笔记操作](https://support.google.com/gemininotebook/answer/16262519?hl=en) | 引用和批评本身均不是本项目独有价值 |
| Open Notebook 提供自托管、多模型、多种资料格式、检索、引用和 REST API。[官方仓库](https://github.com/lfnovo/open-notebook)、[用户指南](https://github.com/lfnovo/open-notebook/blob/main/docs/3-USER-GUIDE/index.md) | “开源、本地、可换模型”不足以区别我们；选云端模型仍涉及外部处理 |
| Open Notebook 的 Transformations 可定制处理内容的提示与共同规则。[官方说明](https://www.open-notebook.ai/features/transformations.html) | “统一规则+连续加工”也存在直接替代，不能以 CONTENT.md 文件名作为优势证明 |

比较基于官方能力与当前代码，不是两款竞品的并排质量/性能实测。不能照抄 Open Notebook README 中对 Google “No API”的笼统对照：Google 官方已有 Enterprise 的 notebook/source API，当前相关文档标注 Preview；这不等于消费版所有 Studio 功能都可通过该 API 自动化。[Enterprise API](https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/api-notebooks-sources)。

## 2. 已实现工作有什么意义

其意义目前主要在工程底座：文件真源、可恢复写入、Agent 与人工决定分离、版本绑定、后台任务、Obsidian 原生入口。这些组件可以保留，但不能用“30 个测试通过”推导“用户需要这个产品”。测试证明既定规则能运行，没有证明规则带来的额外整理与审查成本值得付出。

当前资料是项目内快照。`domain.py` 要求主要关系位于同一项目，尚没有统一来源更新到跨项目内容的完整影响分析；`handoff.py` 只输出本地文件，`Publication` 只接受手工记录 URL/时间，`LEARNING` 只验证观察文字。不能把这些字段和状态名称当作真实发布与反馈能力。

若最终仍停在捕获→生成→审查→导出，独立维护一个插件与 Kernel 的理由偏弱。合理的替代是使用 Notebook 工具研究、Obsidian 编辑、现有发布工具交付；它应成为我们需要胜过的真实基线。

## 3. 为什么此前止步于批准稿

章程第 18 节明确将 Publishing automation、Analytics、Feedback learning 排除在首版；第 19 节参考流程结束于人工 APPROVED。因此先实现这条垂直切片，有明确的范围依据。

但章程第 1、17、24 节也明确要求 Publication→Learning，并通过 Publishing Adapter 接入渠道。上一轮建议把阶段边界当作主要市场定位，将后半段推迟到留存成立后，削弱了原产品目标。应修正为：**先以一个完整渠道闭环验证产品价值，再扩渠道和扩大试点；不把全流程本身放到遥远的可选清单。**

“插件薄”限制的是运行位置；长时工作仍可在 Kernel/外部工具执行。“不重建 CMS”限制的是重复建设；可以调用现有发布能力并管理其状态与回执。这两条都不要求用户自己记住整条流程走到哪里。

## 4. 恢复后的产品承诺

目标：作者给出方向、资料范围与关键判断，系统持续管理从选题到发表、修订、反馈和再次利用的工作；每一项成功状态都有对应证据。

| 阶段 | 用户得到的结果 | 当前 v0.3 | 完整闭环验收要求 |
|---|---|---|---|
| 管理 | 材料库、选题、目标读者、项目计划和复用关系 | 部分：项目与材料快照 | 同一来源被多项目采用时保留共同身份与各自版本，能解释更新影响 |
| 研究 | 可选择研究工具、导入其报告与原始来源 | 部分：已捕获材料内论证 | 外部研究报告不能冒充原始证据，保留原始来源及导入版本 |
| 创作 | 主稿与渠道稿持续修订 | 部分：主稿、单项目自动流程 | 各渠道稿可追溯主稿，编辑差异保留，不静默覆盖 |
| 判断 | 只处理证据不足、分歧、关键修改与最终决定 | 已有基础 | 规则解释具体；资料/主稿/渠道稿变化使对应批准失效 |
| 发布 | 选定渠道、账号、内容预览，确认后投递与回读 | 缺失：仅本地 Markdown 交接 | 有远端 ID/URL、内容版本和状态；远端草稿、提交成功、实际发表分开 |
| 维护 | 发现问题后修订已发布内容，追踪渠道差异 | 缺失 | 重试不重复发文；超时未知结果先查询；更新失败不伪称一致 |
| 反馈与复用 | 将实际反馈变成修订与下个项目的依据 | 部分：手工观察字段 | 反馈有来源、时间和所属版本；生成规则建议，由人确认后用于下一项目 |

最有意义的场景：一份资料用于两篇文章，其中一篇已有渠道版本发表；资料改变后，系统指出受影响内容，组织复核和修订，确认后更新对应渠道，保存回执，并把纠错经验用于下一篇。**这才是值得验证的差异化假设，当前尚未完整实现，也不能声称竞品永远做不到。**

## 5. 实施顺序与边界

1. **保留底座，重组日常界面。** 用户看到材料、选题、进行中、待判断、待发布、已发布；领域关系由系统维护。不能把减轻操作简化为隐藏信息或自动通过审查。
2. **先补一个真实发布渠道。** 选择实际使用且存在可用接口的渠道，打通预览、账号/目标确认、投递、远端回读、回执落盘、失败恢复。Ailu 仅在公开接口、版本、平台支持均确认后作为适配对象；普通 Markdown 导出不算接通。实际账号与发表对象需明确后才能验收对外发表。
3. **随后接上发布后修订与反馈。** 第一版可以由用户导入反馈和数据，不要求先做自动爬取。重要的是反馈能定位内容版本，促成一次修订或下一次选题，并留下判断依据。
4. **再补跨项目复用与外部研究适配。** 来源身份与版本优先。Open Notebook 可通过经过验证的 API 做可选研究能力；Google 能力按消费版/企业版具体接口决定，先支持可追溯导入，不预设一个不存在的通用自动化接口。
5. **以端到端任务验收和试点，而非页面数量验收。** 管理资料→研究→成稿→人工批准→真实渠道回执→反馈→修订或下一项目，至少一个真实闭环通过。再比较整段耗时、工具切换和返工，不能仅比较生成速度。

不建议为了竞争重新建设通用 RAG、聊天、播客、多模型管理和 CMS。若直接改造 Open Notebook，其研究能力可复用，但会引入另一套工作台及部署依赖；与章程的 Obsidian/Markdown 中心需要重新协调。当前更合理的是可选适配，避免强制用户同时安装两套复杂系统。

## 6. 完成标准修正

保留“v0.3 工程切片通过”这个事实；撤回将它视为完整内容生产产品的任何暗示。后续发布必须分别报告：本地门禁、远端草稿投递、实际发表、远端核验、发布后反馈。模拟服务通过只能证明协议处理，不能替代真实渠道成功。

本次仅修正研究、定位和后续验收定义，没有对外发布或声称新增全流程已实现。原始章程保持不变；从管理到发布与反馈的目标在用户本次指正后重新置于产品主线。
