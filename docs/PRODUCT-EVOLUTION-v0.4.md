# OpenContent v0.4：竞争点、取舍与进化

本决策承接 2026-09-08 的 [Obsidian/Ailu 研究](MARKET-STRATEGY.md) 与 [Notebook 补充比较](NOTEBOOK-COMPETITION-AND-FULL-LIFECYCLE.md)。公开能力依据见这两份报告；下面关于偏好、留存和差异化的是待验证产品判断。

## 应当争取的用户

每月持续写教程、研究说明、知识通讯，并反复使用 Vault 资料的作者。一次性问答、泛化总结、播客生成、纯文学写作目前不应是核心获客场景。产品承诺是“这篇内容从哪里来、现在该做什么、哪个版本已发表、下次如何改进”，而不是“又一个更聪明的聊天框”。

| 对照 | 对方已有优势 | OpenContent 可以验证的竞争点 | 目前劣势及应对 |
|---|---|---|---|
| Gemini Notebook | 来源研究、引用问答、多种内容输出、易开始 | Vault 中跨项目来源版本、具体批准到发表回执及后续经验 | 研究与素材格式明显较窄；允许用户在 Notebook 研究，显式捕获可核对的原始来源 |
| Open Notebook | 自托管、多模型、检索与转换、API | Obsidian 原生入口与内容生命周期状态；无需新增研究数据库 | 本地与可换模型并不独有；未来按实际需求接其研究 API，当前不声称已集成 |
| Ailu | Agent 编辑、平台交付及发布前校验经验 | 来源改动如何影响已批准/已发表内容，反馈如何复用 | 平台和编辑能力较窄；保留普通 Markdown 交接，先验证微信，不宣称私有 API 接通 |
| Obsidian 插件组合 | 熟悉的捕获、模板、检索、长文写作 | 减少跨工具复制状态、重复找材料、遗忘发表核验和经验 | Python 安装、门禁步骤及第二个进程增加成本；低频动作不能强制用户走全部流程 |

文件真源、人工门禁和接口适配只是工程条件。只有在完整任务中节省时间、减少错误，并促成作者自主回来，才有用户价值；现有测试不能替代这种证据。

## 日常使用为什么可能成立

第一分钟从已有笔记或选区进入；项目和关系尽量自动建立。下一次打开工作台时能继续当前文章，看到待判断项和计划日期。资料变化时材料库提供比较、刷新、受影响项目与稿件；发布台保存草稿/发表的确切状态，未知结果只读核验；读者反馈经人确认后直接进入下一篇。这些入口已加入 v0.4。

仍需改善：首次安装不应要求非技术用户理解 Kernel；正文图片和排版不足会迫使作者回到微信；“证据与五轴审查”可能对普通短帖过重；严格回读可能因平台 HTML 整理出现保守冲突。先记录真实失败样本，再决定如何改进，不通过放宽内容核验来制造成功。

## 接下来的实施顺序与验收

1. **真实首篇**：有权限的公众号、真正可公开的批准稿、真实封面，完成草稿 → 发表 → 回读 → 反馈 → 下一项目。状态：等待账号配置。此项未过，不能声称渠道已获生产验证。
2. **实际排版兼容**：收集微信保存前后差异，增加正文图片上传和有限样式；仅在可解释、内容不丢失的前提下扩展规范化比对。禁止静默接受语义内容变化。
3. **来源纠错任务**：同一材料用于两项目，其中一篇已发表。原笔记改变后，作者可识别受影响内容、修改并重审；微信原链接修改在后台处理，新版本另发有独立回执。本轮测试覆盖来源变更阻断及已发表稿修订重审，尚缺真实平台纠错观察。
4. **反馈采集**：先用人工数据记录证明反馈被采用，再按账号权限实现官方统计接口。指标必须带日期、统计口径和发表版本；不把点赞数直接变成写作规则。
5. **留存与安装**：按 [四周试点](PILOT-PLAN.md) 用现有组合为基线，测总完成时间、切换次数、重复录入、恢复时间、第二篇自主返回率；优先改善实际最大的成本，再考虑更多渠道或模型。

取舍结论：从管理到发布及反馈是本项目的产品主线，单渠道先行是实施顺序。当前 v0.4 软件闭环已经建立；真实账号、实际编辑质量和持续使用价值仍需分别验证。
